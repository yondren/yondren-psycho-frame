# Agent Note: 门禁内容快照与升级边界加固

Status: proposed

## Problem

[项目评估](../../../reports/project-assessment.md)的 F01—F12 涉及提交内容检查、hooks、升级所有权、
任务生命周期、CLI 合同和发布流程。正常路径测试通过，仍存在错误放行与意外写入的边界。

## Proposal

修复范围覆盖 F01—F12，分六个可独立验收的任务实施。本提案是用户后续派发任务的依据；
本轮只完成计划和现有工作区收尾，不启动这些修复任务、不预创建 IN_PROGRESS 任务卡。

### 顺序与任务拆分

| 顺序 | 建议 task_key | 修复项 | 预期效果 | 依赖 |
| --- | --- | --- | --- | --- |
| 1 | commit-content-guard | F01、F04 | 检查真正待提交的内容；删除决策不能冒充新增或更新 | 无 |
| 2 | task-hook-lifecycle | F02、F09 | 开任务后原 hook 继续生效；成功返回的任务一定满足纪律 | 无 |
| 3 | upgrade-boundaries | F03、F05 | 升级不越界写入，自定义手册和索引关系保留 | 无 |
| 4 | cli-contract-alignment | F10、F11、F12 | 子目录诊断准确、链接规范明确、稳定版升级提示正确 | 无 |
| 5 | ci-onboarding-contract | F06、F07 | 教程可从空目录执行，PR 在合入前验证交付路径 | 1—4 |
| 6 | release-resume | F08 | 已验证产物直接发布，半发布可恢复，过期基线不发布 | 4—5 |

前三项是发布前的可靠性门槛。四至六项完善消费方体验和交付恢复。每项都单独建 worktree，
完成代码、针对性测试、文档和决策记录后再合流；具体执行与合流按当时用户授权和工作模式。

### 1. commit-content-guard

涉及 [destroy.mjs](../../../packages/psycho-frame/src/destroy.mjs)、
[change-scope.mjs](../../../packages/psycho-frame/src/change-scope.mjs)及相应测试。

- 保留四层路径输出的兼容性；内部增加可区分 index、工作树与提交的内容来源。
- 提交前扫描 index blob，工作树安全不能抵消 index 命中。
- 对显式 base..HEAD 的提交范围检查相应提交内容，避免仅检查最终树而漏掉中间提交；
  不扩展成扫描全仓库所有历史。
- 决策要求按 A/M/有效重命名目标及有效 Markdown 记录判断，D 状态不能满足条件。
- 不回显识别内容；读取失败、超大或二进制跳过行为必须有明确回执，不能伪装成已检查。

达到效果：门禁输出能说明“检查了哪个内容版本”，准备提交和准备推送的检查范围可审计。

### 2. task-hook-lifecycle

涉及 [worktree.mjs](../../../packages/psycho-frame/src/worktree.mjs)、CLI 与任务 cookbook。

- 创建前识别已有 hooks 来源和路径，优先保留执行链并隔离可写安装目录。
- 对无法安全衔接的自定义 hooks 明确拒绝并给迁移步骤，不静默指向空目录。
- DONE key 默认拒绝重用，恢复未完成任务与创建新任务明确区分；不隐式重开历史任务。
- 幂等返回前核对分支、任务卡、报告和 hooks；半完成创建可修复或给精确清理指引。
- 出错时不遗留“显示成功但 task check 立即失败”的状态。

达到效果：开 worktree 不削弱消费方已有保护；成功回执具有可验证的后置条件。

### 3. upgrade-boundaries

涉及 [upgrade.mjs](../../../packages/psycho-frame/src/upgrade.mjs)、
[cookbook.mjs](../../../packages/psycho-frame/src/cookbook.mjs)、模板及升级说明。

- 写入前预检全部目标和父级实际路径；默认拒绝越出项目根的符号链接。
- 文件链接、目录链接、失效链接以及同名非文件目标均有明确处理；不能先写一半再发现
  可提前识别的路径错误。
- 对 cookbook 索引采用可保留用户扩展项的合并策略，补入模板条目时不移除自定义条目。
- 明确模板控制内容与用户扩展内容的所有权，输出逐文件动作和备份/恢复清单。
- 保留 dry-run、配置增量合并及 README 保留语义；不借此改写全部用户文档。

达到效果：升级范围可预览，用户新增手册仍然可发现，失败影响与回退位置清晰。

### 4. cli-contract-alignment

涉及 CLI、init、verify-docs、self-update 与 release 的共用契约。

- doctor 无显式目标时使用 Git 根，与 verify/mode 一致；显式目标仍尊重用户输入。
- 仓库 Markdown 要求相对路径，网站内容允许站内根链接；按明确文件归属处理，避免修复
  Unix 绝对路径后误伤官网生成页。
- 明确支持的 Markdown 子集，用真实文档反例校验围栏、锚点及复杂链接。
- 收敛版本比较，正确处理 RC 到 stable、数值预发布标识和 build metadata；非法版本不能
  被静默规整为合法值。保持零运行时依赖。

达到效果：相同命令在子目录中不误报，路径规则有明确边界，版本提示与发布计算一致。

### 5. ci-onboarding-contract

涉及 [CI](../../../.github/workflows/ci.yml)、[官网工作流](../../../.github/workflows/docs.yml)、
教程、模式说明、模板和消费方冒烟。

- 区分核心 CLI 的 Node 支持下限与完整 pnpm 工作流前置条件；保留 Node ≥18.20 的发布包
  声明时，CI 必须增加最低版本检查，开发和网站构建仍使用满足 pnpm 要求的 Node。
- 提供显式 CI 检查合同：保留可在 CI 运行的文档、提交、凭据和决策检查，将本地 worktree
  存在性与本地命令矩阵独立处理。具体 CLI 参数在该任务提案中定稿，不通过隐式 CI 环境
  判断静默关闭安全检查。
- PR 增加相关网站构建及 tarball 安装/create/verify 冒烟，CI 不使用真实发布凭据。
- 将完整教程作为消费方场景验证：环境准备、Git 初始化和基线、开任务、决策报告、
  验证、提交、合流和状态收尾；纠正 pnpm doctor 与模式数量漂移。
- 按涉及平台补 hooks/路径回归，避免仅有字符串级断言。

达到效果：用户跟随文档可完成第一次任务；destroy 配置不再意外破坏 CI；
构建或分发缺陷能在 PR 合入前发现。

### 6. release-resume

涉及 [release.mjs](../../../scripts/release.mjs)、发布 cookbook 与独立的发布流程测试。

- prepare 前检查任务状态、干净工作区、版本、tag 冲突、HEAD 与远端精确 OID。
- 分离准备、验证、发布、核对、推送，记录版本、产物摘要及阶段结果。
- 实际发布通过检查的 tarball，不从工作区重新产生另一份产物。
- 验证当前待发布内容的测试和打包结果；仅“旧 CI 曾通过”不作为本次成功证明。
- 第二包失败后可继续同一版本；核对已发布包与预期产物后跳过它，只重试缺失部分。
- 远端状态变化、tag 冲突或产物不符时停止，输出可恢复位置；不强推、不自动覆盖已发布版本。
- 通过本地假 registry/命令替身测试恢复路径；真实发布、推送另按用户授权执行。

达到效果：减少半发布后的人工猜测，保证验证对象与发布对象一致，并能够安全恢复。

### 工程约束与暂不纳入项

- 保留零运行时依赖、Markdown + Git 载体、现有知识分层和默认工作模式。
- 每项修复保持清晰的错误输出；已有 JSON 输出不无说明地破坏消费者。
- 先实现有判别力的边界反例，再检查正常路径；覆盖率不作为唯一验收标准。
- 文件或配置格式如需迁移，必须同步模板、upgrade 和消费方测试，并给回滚说明。
- 本轮不做新的工作模式、向量检索、完整上下文打包、国际化或官网视觉重设计。
- 不把历史明确延期的 branch-hygiene 流程修改隐式启动。
- 工作量沿用评估的分阶段估计作为参考，正式任务派发时根据设计与平台范围重新估算。

## Alternatives considered

**只改提示和文档** — 不采用：不能防止实际错误放行或越界写入。

**只提高覆盖率阈值** — 不采用：高行覆盖率仍会漏掉 Git 快照和跨模块组合场景。

**一次重写全部 CLI** — 不采用：现有正常路径可用，全面重写会扩大回归面。

**把所有检查永远本地跑满** — 不采用：违背最窄验证分工；本地覆盖改动面，CI 承担平台及交付矩阵。

## Acceptance criteria

| 对应任务 | 必须通过的行为验证 |
| --- | --- |
| 1 | index 命中、工作树安全仍失败；中间提交命中可发现；错误不含识别内容；只删决策不能满足要求 |
| 2 | 原拒绝型 hook 在新 worktree 仍拒绝；DONE key 不隐式重开；幂等或恢复后 task check 通过 |
| 3 | 外部链接目标逐字节不变；非法目标预检失败不产生部分计划写入；自定义手册和索引关系保留 |
| 4 | 子目录 doctor 不误报；Unix 绝对路径规则和网站根链接各按合同处理；RC→stable 与数值标识比较正确 |
| 5 | 全新消费方从教程走完任务；声明下限被测试；PR 能拦官网构建/打包失败；CI 不静默跳过安全检查 |
| 6 | 第二包失败后同版本可继续；已发布包摘要核对；真实发布文件就是受测文件；过期基线和 tag 冲突在不可逆操作前被拒绝 |

每项交付须包含：复现到回归测试的映射、最窄验证记录、模板与文档同步、决策生命周期更新、
任务收尾。最后在 CI 完成支持平台矩阵，再安排新版本发布。

## Risks

- hooks 来源和平台差异可能要求用户迁移；不能承诺任意未知 hook installer 无感兼容。
- Git 历史扫描会增加开销，应限制在显式范围并缓存相同 blob，不扫描无关历史。
- 严格路径检查与链接规则会影响原有消费方，必须给出明确错误和迁移方法。
- 跨 registry 与 Git 没有全局事务；恢复记录只减少不确定性，不使发布可撤销。
- CI 与模式合同需谨慎设计，不能用“让 CI 变绿”的跳过开关掩盖高优先级检查。
